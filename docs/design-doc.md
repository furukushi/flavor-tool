## 1. 目的

キャラチャットツールの掛け合いに対して追加情報を提供する「フレーバー」を、作成・管理するための専用ツール（単独アプリ）を新規に作る。

- フレーバーは、背景・関係性・場所・時間などの「状況の追加情報」を構造化して保持する単位である。
- 本ツールで作成したフレーバーをテキスト出力し、キャラチャット側へ貼り付けることで、AIへ送信する追加プロンプトとして扱えるようにする。
- 将来的にキャラチャット側へ「フレーバー」機能を正式追加した際（第2フェーズ、§11）、フレーバーは現在の「背景情報」の代わりとなり、チャット毎に複数設定できるものとする。本ツールはその受け入れ先ではなく、フレーバーの作成・保管・出力に専念する。

## 2. スコープ

### 2.1 本フェーズ（第1フェーズ）で作るもの
- フレーバーの作成・編集・削除・一覧表示
- 種別（カテゴリ）の事前登録・管理
- JSON出力（エクスポート）とJSON取り込み（インポート）による登録
- テキスト出力（コピー用整形テキストの表示）と、複数フレーバーの複合コピー（§6.6、その場の組み立てのみでセット保存はしない）
- AI自動作成（§17。編集内容をキューへ入れ、Muse側が仲介生成して埋める）

### 2.2 本フェーズで作らないもの
- キャラチャット本体への組み込み（フレーバー選択UI、生成プロンプトへの自動注入）。第2フェーズとして別途設計・確認する。
- フレーバー同士の自動合成（AI等が複数フレーバーの内容を要約・統合すること）。§6.6の複合コピーは内容を変えず区切って連結するだけであり、自動合成には当たらない。
- 複数ユーザー・共有機能。
- お気に入り（ピン留め）、A5矛盾警告、B5常時プレビューは見送り（レビュー格付けに従う。§14・§15参照）。

## 3. 用語

| 用語 | 意味 |
|---|---|
| フレーバー | 本ツールで管理する1件の追加情報。名前・種別・概要・影響度・追加説明・画像を持つ |
| 種別 | フレーバーの分類。背景・関係性・場所・時間などが初期候補。ツール全体で共通のマスタとして事前に登録する |
| 追加説明 | フレーバー毎に自由に増やせる「項目名＋内容＋役割」の組 |
| 役割 | 追加説明の項目が持つ選択式の属性（事実／振る舞い／禁止／条件／具体例／その他）。出力整形に使う |
| デフォルト項目 | 種別毎に設定できる追加説明の項目名＋役割のテンプレート。その種別を選んだフレーバーに初期項目として提示される |
| テキスト出力 | フレーバーの内容をキャラチャットへ貼れる形に整形したテキスト |
| 使用（使った） | コピーボタンを押してクリップボードへの書き込みが成功した時点（単体・複合共通）。表示・プレビューでは使用にならない |
| 複合コピー | 複数フレーバーを内容を変えずに区切って連結し、1テキストとしてコピーすること |
| 自動生成ジョブ | AI自動作成のキュー1件（§17） |

## 4. フレーバーのデータ仕様

すべてのフレーバーが持つ共通項目:

| 項目 | 型 | 必須 | 仕様 |
|---|---|---|---|
| 名前 | 文字列 | 必須 | 空欄不可 |
| 種別 | 種別IDの配列 | 任意（複数選択可） | 事前に登録された種別からのみ選択できる。フレーバー側でその場で新規種別は作れない。未選択（無分類）も可 |
| 概要 | 文字列（複数行） | 任意 | フレーバーの要約 |
| 影響度 | 整数 0〜100（%） | 必須（初期値 50） | スライダー＋数値入力、1%刻み。0%も最弱として扱い、指示文を持つ（§14 A1）。選択UI直下に現在の%に対応するAI向け指示文を常時表示し、%変更に即時連動させる。利用者が見る文面と出力に含まれる文面は同一 |
| 追加説明 | 項目の配列 | 任意 | §5参照。順序を持つ |
| 画像 | 画像1枚 | 任意 | 一覧表示でフレーバーを区別するためだけに使う。テキスト出力・JSONには含めない。形式は png/jpeg/webp、読み込み失敗時は頭文字アイコンへフォールバックする |
| 作成日時 / 更新日時 | 日時 | 自動 | |
| 最終使用日時 | 日時 | 自動 | コピー成功時に更新（§3「使用」の定義） |

## 5. 追加説明の仕様

- 追加説明は「項目名（ラベル）」「役割（選択式）」「内容（テキスト、複数行可）」の組を、ユーザーが任意に追加・削除できる。
- 例: 項目名「具体的な説明」／「補足」／「関連する項目」（「関連する項目」は自由記述の項目であり、他フレーバーへのリンク機能ではない。決定済み）
- 役割の選択肢: 事実／振る舞い／禁止／条件／具体例／その他。項目名は自由入力のままとし、役割のみ選択式にすることで、出力時の分離・整列（禁止事項の独立表示、役割順の整形）を機械的に実現する。
- 同じ項目名は1フレーバー内に1件まで。項目数は20件まで。
- 項目の並び順はユーザーが決めた順序を保持する。テキスト出力では役割順（事実→条件→振る舞い→具体例→禁止）に整列し、同役割内はユーザーの並び順に従う。
- 種別毎のデフォルト項目:
- 種別マスタに「デフォルト項目（項目名＋役割）のリスト」を設定できる。
- フレーバーで種別を選択した瞬間に、その種別のデフォルト項目が、まだ存在しない場合に限り末尾へ空項目として補われる。複数種別の場合は種別の選択順に合体し、同名項目は1件に統合する。
- すでに内容が入っている同名項目は上書きしない。種別の選択を外しても、追加済みの項目は削除しない。
- 種別マスタのデフォルト項目を後から変更しても、既存フレーバーには伝播しない（作成・編集中の補充にのみ効く）。

## 6. 機能要件

### 6.1 種別管理
- 種別はフレーバー作成の前に登録が必要な共通マスタとする。種別の新規作成は管理画面からのみ行う。
- 種別の追加・編集・削除ができる管理画面を用意する。
- 種別が持つ情報: 名前、デフォルト項目リスト、表示順。
- 種別名は一意とする（前後空白を除去して照合）。改名は可能だが、改名時は「過去に出力したJSON（名前照合）と一致しなくなる」注意を表示する。
- 初期種別として「背景」「関係性」「場所」「時間」を登録しておく。
- 使用中の種別も削除できる。削除時は確認ダイアログを出し、紐付くフレーバーからはその種別だけが外れる。

### 6.2 フレーバーの作成・編集・削除
- 作成フロー: 名前入力 → 種別選択（複数可） → 概要入力 → 影響度選択（直下に指示文を常時表示・連動） → 追加説明の編集 → 画像選択（任意） → 登録。
- 登録後、一覧に表示される。一覧から後から編集できる。編集は全項目を対象とする。
- 削除は確認ダイアログ付きとする。
- 複製ボタン: 既存フレーバーを複製して新規作成できる。画像も複製し、最終使用日時は引き継がない。名前は「〜のコピー」とし、衝突時は (2)(3)… を付ける。
- 編集画面には「プレビュー」ボタンを置き、テキスト出力形式（§9.2）をその場で確認できる（常時表示はしない）。編集中の離脱時は確認ダイアログを出す（自動下書き保存はしない）。
- AI自動作成の入口も編集画面に置く（§17）。生成待ち・生成中のフレーバーは編集できない。

### 6.3 一覧表示
- 各フレーバーは画像（あれば）＋名前＋種別＋影響度（数値とバー表示）が分かる形で表示する。
- 並び替え: 「あいうえお順」と「使った順」から選択できる。
- あいうえお順の定義: 名前の文字列照合順（ひらがな→カタカナ→漢字→英数字のコード順）を五十音順とみなす。読み仮名欄は設けない。同名の場合は作成日時の古い順。
- 使った順: 最終使用日時の新しい順。一度も使っていないフレーバーは末尾にあいうえお順で並べる。
- 種別によるフォルダ分け: 表示モードを切り替えると、全種別のフォルダが種別マスタの表示順に並び、各フォルダ内に該当フレーバーが表示される。複数種別を持つフレーバーは該当する各フォルダに表示される。種別未選択は「無分類」フォルダ。フォルダ内でも選択中の並び替えが効く。
- 検索: 名前・概要・追加説明の内容・種別名を対象とする簡易検索欄を置く。

### 6.4 テキスト出力
- 一覧の各フレーバーに「テキスト出力」ボタンを置く（操作はこのボタンに集約し、別途のコピーボタンは一覧行に置かない）。
- 押すと、そのフレーバーの全入力情報をまとめたテキスト（§9.2）を表示し、コピーボタンでコピーできる。クリップボードが使えない環境ではテキスト選択による手動コピーができる状態にする。
- コピー成功時に最終使用日時を更新する。コピー失敗時は更新しない。
- 出力画面には文字数（目安）を表示する。
- 画像はテキスト出力に含めない。

### 6.5 JSON出力・取り込み
- フレーバーをJSON形式で出力できる。出力単位は「1件」と「全件一括」の両方。単体・一括とも同一のラッパー形式（§9.1）に統一する。
- JSONの主用途は受け渡し（他環境・第2フェーズ連携への移行を含む）と位置付ける。画像は含まないため、画像まで含めた完全バックアップにはならないことを出力画面に明記する。
- 取り込み時の検証と失敗扱い:
- JSON構文エラー、または format / format_version が想定外の場合は全体エラーとして1件も登録しない。
- 構文が正しい場合はフレーバー単位で検証し、正常なものだけ登録する（部分成功）。失敗したフレーバーは理由を件別に表示する。名前の欠落は検証エラー。
- 未登録の種別名が含まれていた場合、その種別を自動で種別マスタへ追加し、取り込み結果として通知する。
- 同名フレーバーが既にある場合は上書きせず別件として登録し、結果を通知する。

### 6.6 複合コピー（複数フレーバーの一括出力）
- 一覧で複数フレーバーを選択し、選択順を並べ替えて、1つのテキストとしてまとめてコピーできる。セットとしての保存はしない（毎回その場で組み立てる）。
- 形式: 全体の先頭に範囲宣言を1回だけ置き、各フレーバーは開始マーカー付きで区切る（§9.3）。複合時は影響度の指示文は個別に付けず、全体宣言として「最も高い影響度の段階文面」を1つだけ置く（最優先の並立を避ける正規化）。個別フレーバーには名前・%のみを示す。
- 同一フレーバーの重複選択はできない。
- 複合コピーの成功時、対象全フレーバーの最終使用日時を更新する。合計文字数（目安）を表示する。

## 9. 出力フォーマット

### 9.1 JSON形式（flavor-export / 1.0）
```json
{
"format": "flavor-export",
"format_version": "1.0",
"exported_at": "2026-11-26T10:00:00+09:00",
"flavors": [
{
"name": "豪雨の日のコロニー",
"types": ["背景", "場所"],
"summary": "激しい雨が降り続く日の出来事。",
"influence": 70,
"extra_fields": [
{ "label": "具体的な説明", "role": "事実", "value": "外出は困難で、室内の会話が中心になる。"},
{ "label": "補足", "role": "その他", "value": "雷の音が時折響く。"}
]
}
]
}
```
- 種別はIDではなく名前で出力し、取り込み側のマスタと名前で照合する。
- 画像は含めない。

### 9.2 テキスト出力形式（単体・確定例）
```
【フレーバー開始】豪雨の日のコロニー
種別: 背景 / 場所
影響度: 70%（積極的に反映すること。迷った場合はこのフレーバーを優先すること。ただしキャラ設定の範囲内で反映すること）
概要: 激しい雨が降り続く日の出来事。

■ 具体的な説明
外出は困難で、室内の会話が中心になる。

■ 補足
雷の音が時折響く。
【フレーバー終了】
```
- 単体出力にも開始／終了マーカーを付け、複数貼り付け時の境界を機械的に判別できる形にする。範囲宣言（「以下は追加設定である」旨）は単体には付けず、複合時のみ先頭に1回置く。
- 空の項目（概要が空、内容が空の追加説明）は出力から省く。
- 「禁止」役割の項目は最後に独立した見出し「■ してはいけないこと」相当としてまとめ、他の項目と混ぜない（項目名は元のラベルを使う）。

### 9.3 複合コピー形式（確定例）
```
以下はこの掛け合いへの追加設定である。全体を通して、最も高い影響度は80%であり、その段階の指示は「積極的に反映すること。迷った場合はフレーバーを優先すること。ただしキャラ設定の範囲内で反映すること」である。

【フレーバー開始】豪雨の日のコロニー
種別: 背景 / 場所
影響度: 80%
概要: 激しい雨が降り続く日の出来事。

■ 具体的な説明
外出は困難で、室内の会話が中心になる。
【フレーバー終了】

【フレーバー開始】旧知の間柄
種別: 関係性
影響度: 40%
概要: 子供の頃からの幼馴染である。

■ 関係の内容
遠慮なく言い合えるが、肝心なところでは互いを気遣う。
【フレーバー終了】
```
- 各フレーバーは §9.2 と同じ項目構成で出力するが、影響度の指示文は個別に付けない（先頭の全体宣言に正規化済み）。マーカーは「【フレーバー開始】名前」「【フレーバー終了】」で固定する。
- 全体宣言の文面は、複合時は「フレーバーを優先すること」と言い換える形を正本とする（§13の単体用文面「このフレーバーを優先すること」との差は意図的なもの）。

## 10. バリデーション・例外

- 名前が空のフレーバーは登録できない。

## 17. AI自動作成機能（2026-11-26 ユーザー追加依頼）

### 17.1 概要
フレーバーの編集中に「AI自動作成」を選択すると自動生成オプションが開き、ユーザーが用意した一部の項目を土台に、残りの項目をAIが判断して埋める。生成は即時実行ではなくキュー方式とし、Muse側が仲介して実行する（キャラチャットの生成仲介と同じ方式。仲介に別AIを使ってもよい）。

### 17.2 入力（自動生成オプション）
- 前提条件: **名前が入力されていなければ生成はできない。名前はAI生成の対象にしない**（決定 §19-1）。名前はフレーバーの識別として常にMuse側へ渡るが、AIが名前を生成・変更することはない。名前未入力の場合はキューへ入れず、その旨を表示する。
- 土台にする項目の任意選択: 種別・概要・影響度・追加説明の各項目について、ユーザーが入力済みの内容のうち「土台として渡すもの」を任意に選択できる。
- 方針リクエスト文章: 自動生成の方針について、ユーザーが自由文でリクエストを送ることができる（任意）。
- 基本方針（固定。ユーザーにはオプション画面で明示する）: 「必要な情報だけを端的に書く。冗長な説明は書かない」。
- 土台ゼロの扱い: 土台として選択した項目が無く、方針リクエスト文章も無い場合はキューへ入れない（最低限、土台1項目か方針リクエストのどちらかが必要）。

### 17.3 生成規則（Muse側へ渡す指示の要点）
- 生成結果は対象フレーバーへ**上書き保存**される（決定 §19-3）。名前以外の全項目（種別・概要・影響度・追加説明）が上書き対象になる。
- 「元の文脈を考慮するか」は自動生成全体の設定（アプリ全体設定、§17.7）で選択できる。
  - 考慮する: 土台として選択した項目を中心に、既存の入力内容全体を文脈としてAIへ渡し、AIは文脈を踏まえた内容で上書き分を生成する。
  - 考慮しない: 土台として選択した項目と方針リクエストだけをAIへ渡し、土台以外の既存内容は文脈に含めない。生成結果は既存内容を置き換える。
- 追加説明は、必要と判断すればAIが項目（ラベル＋役割＋内容）を勝手に足してよい。役割は §5 の選択肢から選ぶ。
- 種別は既存の種別マスタからのみ選択する（AIが新規種別を作ることはしない）。
- 影響度は、内容の強さに応じて 0〜100 で判断する。
- 概要・追加説明の内容は基本方針通り、必要な情報だけを端的に書く。
- 反映前の検証（決定 §19-5）: Muse側は生成結果をアプリへ渡す前に §5 の制約（同名項目は1件まで、項目数20件まで、役割は選択肢内、種別は既存マスタ内、影響度0〜100）で検証し、違反部分は切り捨て・補正する。名前が結果に含まれていても代入しない。

### 17.4 キューと実行
- 「キューに入れる」ボタンを押すと、その時点の入力内容がフレーバーとして保存された上で、自動生成ジョブがキュー（状態: queued）に入る。投入時点の全項目スナップショットをジョブに記録する（履歴・照合用）。
- キュー投入中（queued / processing）のフレーバーは編集・削除・複製・出力ができない（ロック表示にする）。
- 同一フレーバーに対して有効なジョブは1つまで（二重投入不可）。複数フレーバーのジョブは投入順に処理する。
- 実行トリガー（決定 §19-2）: Muse側が1分間隔でキューを確認し、queued があれば自動で実行する（キャラチャットの signal sweep と同じ方式）。ユーザーがチャットで依頼しなくても進む。
- **Claudeに関する処理はアプリ内に埋め込まない**（決定 §19-6）。アプリはキュー（ジョブの登録・状態・結果の受け口）だけを持ち、生成の実行と結果の代入は全てMuse側が判断して行う。仲介に別AIを使うかどうかもMuse側の判断に属し、アプリは関知しない。
- 完了すると生成結果がフレーバーへ上書き反映され、完了扱い（状態: done）となり、再度編集できるようになる。
- 失敗した場合はロックを解除し、失敗理由を表示する（状態: failed）。再度キューへ入れ直すことができる。
- processing の滞留（仲介側の停止等）への対処もMuse側の責務とし、アプリ内にタイムアウト機構は持たない。ユーザーは次項の強制キャンセルでいつでもロックを解ける。

### 17.5 キャンセル（強制キャンセルを含む）
- ユーザーは queued / processing のどちらの状態でも、そのジョブをキャンセルできる（生成中の強制キャンセルを含む。決定 §19-6）。
- キャンセルするとジョブにキャンセルが登録され（状態: cancelled）、フレーバーのロックは即時解除される。
- キャンセル登録がある場合、Muse側は生成結果が手元にあっても**結果を代入しない**。Muse側は代入の直前に必ずジョブの状態を確認し、cancelled であれば結果を破棄する。
- キャンセルされた実行も履歴に残る（状態: cancelled として記録）。

### 17.6 履歴
- 実行内容は履歴に残す。履歴1件ごとに: 対象フレーバー、投入日時、投入時点の全項目スナップショット、土台として渡した項目、方針リクエスト文章、「元の文脈を考慮するか」の設定値、生成結果（反映した全項目。キャンセル時は破棄した旨）、状態、完了日時、失敗理由（失敗時）。
- 履歴は自動生成履歴表示（§7）から一覧・詳細を確認できる。履歴の編集・削除は第1フェーズでは行わず、保持上限は設けない。対象フレーバーが削除された場合も履歴は残し、フレーバー名で表示する。

### 17.7 自動生成全体の設定
- アプリ全体設定として「元の文脈を考慮するか」（オン／オフ）を持つ。既定値はオン（決定 §19-3の運用として、変更はユーザー指示があった場合のみ）。
- この設定はキュー投入時点の値がジョブに記録され、そのジョブの生成に適用される。設定変更は未実行のジョブには影響しない（投入時点の記録が優先）。

### 17.8 データモデル
§8 の generation_jobs がキューと履歴を兼ねる。実行中ジョブ（queued / processing）の有無でフレーバーの編集可否を判定する（フレーバー側にロック用カラムは持たない）。generation_jobs には §17.6 の履歴項目（全項目スナップショット、土台の選択、文脈考慮の設定値）を保持するカラムを含める。
